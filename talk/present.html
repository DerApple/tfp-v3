The shift

Doing the work is getting cheap.
Coordinating it is not.

Ten agents can write code in parallel today. The hard part is making sure they work on the right things, don't collide, and leave something the next one can use.

The usual reflex

Push vs. pull

Orchestrator pushes

  • One agent plans and assigns work
  • Must know every worker's capacity and skill
  • Single point of failure and bottleneck
  • Its context window limits the whole team

Workers pull

  • Work sits on a shared board
  • Whoever has capacity takes the next item
  • Add or lose a worker: nothing to reconfigure
  • Consistency comes from the board, not a boss

Not a new problem

We have solved this before

Kanban

Toyota, 1950s. Pull work when you have capacity; limit work in progress.

Open source

Strangers pick issues, assign themselves, hand off through pull requests.

Stigmergy

Ants coordinate by changing their shared environment, not by talking.

Tuple spaces

Linda, 1985. Workers atomically take a tuple from a shared space.

The board

A task is a markdown file

---
title: Model-aware picking
status: todo
owner:
deps: [chore-tier]
prio: 2
---
## Goal
Match tasks to models...
## Acceptance criteria
- [ ] tasks have difficulty 1-4
- [ ] failed release raises it

Front matter is state

Only the tool writes status and owner.

deps form a graph

next lists ready tasks, most-blocking first.

Criteria are the contract

Checkable, 30 to 90 minutes of work, tests included.

The protocol

Five verbs an agent needs

VerbWhat it doesGuarantee
nextReady tasks, most-blocking firstDeps are respected
claimTake a task, atomicallyExactly one owner
doneMerge main, run the check, pushMain holds only finished work
releaseGive it back with a noteWork in progress survives
assumeLog a decision a human may revisitNobody waits for an answer

The rules fit on one page (AGENTS.md). Any agent that can run a shell command can join.

Mechanics · claim

git push is a compare-and-swap

StepAgent AAgent B
1Sets status and owner, commitsSame task, same edit, commits
2Pushes first: acceptedPush rejected: not a fast-forward
3CLAIMED, starts workRolls back, sees owner A
4LOST RACE, back to next

The remote ref is the lock. No lock server, no clock sync: whoever moves main first wins, and the loser finds out from git itself.

Mechanics · leases

A crashed laptop can't block the board

claim

Lease starts

The claim records lease_until, 20 min ahead.

heartbeat

Lease renewed

The runner renews it while the agent is alive.

silence

Lease expires

The task is stale and can be claimed again.

takeover

New owner

Starts from wip/<id>, not from zero.

The old owner's next command prints LOST, and it stops. Human claims never expire.

Mechanics · done

Main only ever holds finished tasks

1 · Merge main

Pick up what others finished meanwhile.

2 · Run the check

.taskcheck: lint and tests, on the merged result.

3 · Mark done, push

Code and status land in one go.

Agents never push. A deny rule in the agent settings enforces it; done pushes for them.

Check fails? Nothing is pushed. Fix it and run done again.

When workers are LLMs · 1

Hand over the work, not a retry

Classic job queue

A failed job is retried from scratch. The worker's state is lost, and that's fine: the job is deterministic.

Agent board

  • Commits are backed up to wip/<id>
  • release --note says what is done and what blocks
  • The next owner merges wip first, then continues
  • A failed merge is saved as an attempt to learn from

When workers are LLMs · 2

Agents may reshape the plan

split

Too big? Write 2 to 6 subtasks. The parent waits and later only integrates.

new

Discovered a missing task? Add it with its deps.

hold

Needs a human decision? Park it with the question.

extend

Nearly done? One more session, once.

Guardrails: subtasks can't be split again; two sessions per task, then a review.

When workers are LLMs · 5

Some conflicts are spec problems

The conflictWhat the agent does
Obvious: imports, both added linesResolve, continue; done proves it
Same conflict on every commitAbort the rebase, merge main once
Unclear what the other side meantredo: save the attempt, re-implement on latest main
Two tasks disagree on designrelease with a note, add a task to reconcile

Git sees text. The last row is about meaning: two specs that contradict each other. That goes back to the plan, not into a guessed merge.

Open question · next on the board

Which model should take which task?

The task declares a difficulty

LevelMeaning
1Mechanical: smallest model
2Normal work (the default)
3Hard: a strong model
4The best model available

Escalate on failure

Each failed release or redo raises the level by one.

Reserve scarce models

The strongest model waits for the hardest tasks, but the critical path never waits long.

Deterministic, not self-assessed

LLMs judge their own ability poorly. The runner decides.

Honest limits
