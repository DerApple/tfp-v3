Some conflicts are spec problems

The conflictWhat the agent does
Obvious: imports, both added linesResolve, continue; done proves it
Same conflict on every commitAbort the rebase, merge main once
Unclear what the other side meantredo: save the attempt, re-implement on latest main
Two tasks disagree on designrelease with a note, add a task to reconcile

Git sees text. The last row is about meaning: two specs that contradict each other. That goes back to the plan, not into a guessed merge.

Parallel agents produce merge conflicts constantly, and agents are tempted to resolve them by guessing. The protocol gives them a ladder. Mechanical conflicts: just resolve, the check will catch mistakes. Repeated ones: merge once instead of rebasing commit by commit. Unclear ones: start over on the new main, keeping the old attempt as a reference. And the important one: if two tasks changed the same contract in different ways, that's a contradiction in the plan. The agent escalates it as a new task instead of picking a winner.
